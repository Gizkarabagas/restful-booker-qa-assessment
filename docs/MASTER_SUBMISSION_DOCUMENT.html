SECTION 2: Structured Defect Reports

During exploratory and automated testing against the live demo application, three (3) verified defects were identified. ---

Defect 1: [BUG-001] Frontend Crashes to Unhandled Error Boundary ("This page couldn't load") on Booking Date Conflict (HTTP 409)

* Issue ID: BUG-001 * Severity: Critical (S1) * Priority: High (P1) * Component: Frontend / Booking Modal / Error Handling * Environment: Production Demo (https://automationintesting.online/), Next.js Client, Chrome / Chromium #### Description: When a user attempts to book a room for dates that conflict with an existing reservation, the backend API correctly returns an HTTP 409 Conflict with JSON payload {"error":"Failed to create booking"}. However, the frontend application fails to catch this status code. Instead of displaying a user-friendly error message inside the modal (e.g. "The selected dates are already booked. Please choose alternative dates"), the entire React application crashes and renders Next.js's fallback unhandled error boundary screen: "This page couldn't load. Reload to try again, or go back." #### Steps to Reproduce: 1. Navigate to reservation URL with dates that already have a booking: https://automationintesting.online/reservation/1?checkin=2026-11-10&checkout=2026-11-12 2. Click the blue "Reserve Now" button on the right price summary card. 3. Fill in valid guest details: * Firstname: John | Lastname: Doe | Email: john.doe@example.com | Phone: 0812345678901 4. Click "Reserve Now" inside the modal. #### Expected Result: The modal remains open and renders a prominent warning alert: "The selected dates are already booked or unavailable. Please select alternative dates." All user input is preserved. #### Actual Result: The API call POST /api/booking responds with HTTP 409 Conflict. The UI immediately crashes to a full-page error boundary screen: "This page couldn't load. Reload to try again, or go back." All user input is lost. #### Evidence: * API Response: HTTP/1.1 409 Conflict $\rightarrow$ {"error":"Failed to create booking"} * Screenshot Evidence:

Defect 2: [BUG-002] Missing Phone Number Format Validation (Accepts Purely Alphabetic Strings)

* Issue ID: BUG-002 * Severity: Medium (S2) * Priority: Medium (P2) * Component: Backend API Validation Layer (/api/booking) * Environment: Production Demo (https://automationintesting.online/api/booking) #### Description: The phone number validation on both the client-side and backend API only checks the string length constraint (size must be between 11 and 21). It fails to validate numerical or dialing format. As a result, users can submit purely alphabetic strings (e.g. "abcdefghijk12") as their contact phone number, and the system accepts the reservation with HTTP 201 Created. #### Steps to Reproduce: 1. Send a POST request to https://automationintesting.online/api/booking with payload: 

   {
     "roomid": 1,
     "firstname": "Tester",
     "lastname": "AlphaPhone",
     "depositpaid": false,
     "bookingdates": { "checkin": "2026-12-01", "checkout": "2026-12-03" },
     "email": "test@example.com",
     "phone": "abcdefghijk12"
   }
2. Inspect the HTTP status code and response body. #### Expected Result: The API should validate the phone field against numeric/international phone format and reject with HTTP 400 Bad Request: {"errors": ["Phone number must contain only numbers and valid dialing characters"]}. #### Actual Result: The API responds with HTTP 201 Created and successfully writes the record: 

{
  "bookingdates": { "checkin": "2026-12-01", "checkout": "2026-12-03" },
  "bookingid": 5,
  "depositpaid": false,
  "firstname": "Tester",
  "lastname": "AlphaPhone",
  "roomid": 1
}

SECTION 4: Performance Testing Approach & Analysis (Task 4)

4.1 Scenario & Traffic Assumption

* Baseline Traffic: 5 requests per second (RPS) * Peak Traffic: 20 requests per second (RPS) * Goal: Verify system stability, throughput, and latency thresholds under normal, ramp-up, and peak load on the Booking API (POST /api/booking).

4.2 Workload Model (k6 Stages)

A Ramping Arrival Rate model was selected to simulate real-world guest reservations: 1. Warm-up & Normal Traffic: 5 RPS sustained for 1 minute. 2. Gradual Traffic Increase: Ramp from 5 RPS to 20 RPS over 2 minutes. 3. Peak Traffic Stress: Sustained 20 RPS for 2 minutes. 4. Cool-down / Recovery: Ramp down back to 0 RPS over 30 seconds.

4.3 Key Metrics & Thresholds Selection

| Metric | Threshold | Engineering Justification | | :--- | :--- | :--- | | http_req_duration (p95) | < 500ms | 95% of guests receive booking response within 500ms for smooth user experience. | | http_req_duration (p99) | < 1200ms | Tail latency ceiling to prevent connection timeouts during database writes. | | http_req_failed | < 1% | Acceptable error rate under normal and peak operations (excluding 409 business conflicts). | | checks | > 99% | Ensures booking creation contract and response schema validity. |

4.4 Example k6 Performance Test Script (performance/booking-perf.js)


import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  scenarios: {
    booking_traffic_ramp: {
      executor: 'ramping-arrival-rate',
      startRate: 5,
      timeUnit: '1s',
      preAllocatedVUs: 50,
      maxVUs: 150,
      stages: [
        { target: 5, duration: '1m' },   // Stage 1: Normal Expected Traffic (5 RPS)
        { target: 20, duration: '2m' },  // Stage 2: Gradual Traffic Increase to Peak (20 RPS)
        { target: 20, duration: '2m' },  // Stage 3: Sustained Peak Traffic (20 RPS)
        { target: 0, duration: '30s' },  // Stage 4: Ramp down / Recovery
      ],
    },
  },
  thresholds: {
    'http_req_duration': ['p(95)<500', 'p(99)<1200'],
    'http_req_failed': ['rate<0.01'],
    'checks': ['rate>0.99'],
  },
};

export default function () {
  const url = 'https://automationintesting.online/api/booking';
  
  // Generate unique future booking dates to prevent false 409 conflicts
  const randomDay = Math.floor(Math.random() * 20) + 1;
  const uniqueMonth = Math.floor(Math.random() * 5) + 1;
  const payload = JSON.stringify({
    roomid: 1,
    firstname: 'PerfUser',
    lastname: 'k6Test',
    depositpaid: false,
    bookingdates: {
      checkin: 2028-0${uniqueMonth}-${String(randomDay).padStart(2, '0')},
      checkout: 2028-0${uniqueMonth}-${String(randomDay + 2).padStart(2, '0')},
    },
    email: perf_${__VU}_${__ITER}@loadtest.io,
    phone: '0812345678901',
  });

  const params = {
    headers: { 'Content-Type': 'application/json' },
  };

  const res = http.post(url, payload, params);

  check(res, {
    'status is 201 or 409': (r) => r.status === 201 || r.status === 409,
    'response time OK': (r) => r.timings.duration < 1200,
  });

  sleep(0.5);
}

4.5 Limitations & Risks

* Shared Sandbox DB Lockups: On a public shared instance, concurrent bookings on the same room can produce artificial HTTP 409 conflicts. In production testing, a dedicated pre-prod cluster with automated DB teardown should be provisioned. * Network Jitter / CDN Caching: Direct testing over public internet measures WAN latency rather than raw backend microservice capacity. k6 execution inside the private VPC is recommended for pure service benchmarking. ---
